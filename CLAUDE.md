# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Halves — a self-hosted expense tracker for splitting shared costs (roommates, groups). FastAPI + SQLAlchemy backend, vanilla-JS SPA frontend, no build step. Design principle for every feature: keep it dead simple.

For the full architectural picture (data model, caching, multi-DB sharding, push notifications, PWA), read **`TECHNICAL_OVERVIEW.md`** — it's kept close to current but can lag the newest features (currently missing: categories router, i18n/currency, backup & restore, the uuid5 identity switch — all covered below and in git history). `README.md` has the user-facing setup/config instructions.

## Commands

```bash
# Backend dev server (from backend/, after `pip install -r requirements.txt` in a venv)
uvicorn app.main:app --reload          # http://localhost:8000, serves frontend too

# Tests (from backend/)
pytest                                  # full suite
pytest tests/test_app.py                # one file
pytest tests/test_app.py::test_name -v  # one test

# Docker dev (from repo root) — bind-mounts backend/app, frontend, tests, alembic; --reload
docker compose up --build               # http://localhost:8130
docker compose exec app bash -c "cd /app/backend && pytest"

# New migration after editing app/models.py (shared-DB models)
cd backend && alembic revision --autogenerate -m "describe the change"
# Household-DB models (Expense/ExpenseParticipant/Settlement/BalanceCache) use a
# separate stream — point alembic_household.ini's sqlalchemy.url at a real
# household file already at head, then:
alembic -c alembic_household.ini revision --autogenerate -m "describe the change"
```

No package.json / npm — the frontend is plain JS served as static files, no build/lint tooling for it. Always review autogenerated migrations in `alembic/{shared,household}/versions/` before committing; autogenerate handles additive changes reliably but not renames or data backfills.

## Architecture essentials

**Two separate SQLite databases, two separate SQLAlchemy bases** (`app/database.py`):
- **Shared file** (`SharedBase`): `User`, `Household`, `AppSetting`, `PushSubscription`.
- **One file per household** (`HouseholdBase`, via `app/household_db.py`'s LRU-capped engine registry, cap 128): `Expense`, `ExpenseParticipant`, `Settlement`, `BalanceCache`.
- SQLite can't join or FK across files, so any id crossing the boundary (`Expense.payer_id`, `Expense.created_by_id`, `ExpenseParticipant.user_id`, `Settlement.from_user_id`/`to_user_id`) is a **plain int/str column, not a `relationship()`**. Router code resolves the `User` side itself with one batched query and stitches it onto the Pydantic response (`_stitch_expense_users()` in `routers/expenses.py`, and `balances.py::get_balance_summary()`, are the pattern to follow for any new cross-file lookup).
- Two independent Alembic streams (`alembic/shared/`, `alembic/household/`), both `render_as_batch=True`. `app/migrations.py` runs the shared stream on startup and walks existing household files to catch them up; new household files migrate to head at creation.

**User identity is `uuid5(APP_NAMESPACE, email.lower())`** (`app/identity.py`), not an autoincrement id — deterministic across machines so a restored per-household file's foreign ids always resolve to the same person regardless of which instance they sign up on. `APP_NAMESPACE` is a hardcoded constant; never change it, it would invalidate every existing user id.

**Auth dependency chain** (`app/dependencies.py`), each stricter than the last — pick the weakest one a route actually needs:
```
get_current_user          -> valid JWT, status != removed
  get_current_approved_user  -> status in {approved, moved_out}
    require_household           -> has household_id
      get_current_active_user      -> status == approved (excludes moved_out)
        get_current_admin              -> role == admin
```
e.g. viewing history only needs `require_household` (moved-out members can still see it); logging a new expense needs `get_current_active_user`.

**Balances**: `app/balances.py` computes net position (paid − weighted share of tagged expenses, adjusted by settlements) and runs a greedy min-cash-flow simplification for 3+ people. Results are cached one row per household in `balance_cache`; every write that can change a balance (new/edited/deleted expense, settlement) deletes that household's cache row **in the same transaction as the write**, before commit — never add a write path that skips this, and never add an incremental cache-update path (the only two valid states are "absent" and "exactly what a fresh compute produces").

**Routers** (`app/routers/`): `auth` (signup/login/me/invite), `users` (membership lifecycle: pending/approve/decline/moved_out/removed), `households` (rename, and admin JSON export/restore for backup), `expenses` (CRUD + `PATCH .../shares` for re-weighting), `balances` (cached summary + settlements), `push` (VAPID/subscribe), `categories` (per-household editable expense categories).

**Membership statuses** are more than pending/approved: `moved_out` keeps sign-in but blocks logging new expenses; `removed` blocks sign-in outright (checked in `get_current_user` itself, not just at login, so an already-issued token is invalidated too). Both are reversible. A household must always keep at least one admin — this is guarded on every role/status change; don't bypass it.

**Frontend** (`frontend/app.js`, ~2200 lines, no framework/build step): one `state` object; every user action mutates `state` then calls `render()`, which rebuilds HTML from scratch (`buildHtml()` switches on `state.route`) and reassigns `innerHTML`. Events are delegated at the `#app` root via `data-action`/`data-field` attributes (not per-element listeners) so the full-innerHTML-replace doesn't lose bindings. `frontend/i18n.js` (~680 lines) drives English/Persian translation and per-household currency formatting. Watch for two known footguns when touching render/animation code: recreating a DOM node on every render restarts CSS entrance animations (guarded via `lastRenderedSheet` + suppressing `style.animation`), and a `@keyframes` block animating `transform` fully replaces the base rule's `transform` rather than composing with it (any static transform, e.g. sheet centering, must be repeated inside the keyframes).

**Tests** (`backend/tests/`, pytest, one `client` fixture in `conftest.py` per test): the fixture points `DATABASE_URL`/`HOUSEHOLD_DB_DIR` at fresh temp locations *before* `app.database`/`app.household_db` are imported (env vars are set at module load time, above the imports), then drops/recreates the shared schema and wipes the household-file directory. Follow this pattern for any new test module rather than importing app modules before the fixture runs.
